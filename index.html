    • 원인 분석: REST는 고정된 엔드포인트에서 정해진 응답 구조를 반환하는 방식인 반면, 해당 시스템은 클라이언트가 필요한 필드를 직접 쿼리하는 GraphQL 스펙만을 지원하고 있어, REST 방식으로는 통신 자체가 불가능했습니다.
    • 해결 방법: GraphQL 클라이언트를 도입하여 해당 시스템과의 데이터 연동 레이어를 신규 구축했습니다. 필요한 필드만 선언하여 요청하는 GraphQL의 특성을 활용해 Overfetching을 방지하고 통신 효율을 성공적으로 확보했습니다.
  • [대규모 분산 처리] 전 매장 대상 통합 작업 지시(Broadcasting) 파이프라인 개선
    • 문제 인지 (어쩌다 찾았는지): 전국의 모든 매장에 동시다발적으로 대규모 작업(상품 업데이트, 이벤트 추가, 템플릿 변경 등)을 내려보낼 때, 응답 지연(Timeout)이 발생하거나 일부 매장에 작업이 누락되는 병목 현상이 있었습니다.
    • 원인 분석: 단일 동기식(Synchronous) 구조로 수많은 매장 서버와 통신하려다 보니 병목이 발생했고, 쓰레드(Thread) 및 커넥션 풀 자원이 빠르게 고갈되는 것이 원인이었습니다.
    • 해결 방법: 대규모 작업 지시 로직을 비동기 처리(Asynchronous) 방식으로 개편하고, 메세지 큐(Message Queue) 혹은 청크(Chunk) 단위의 병렬 분산 처리 아키텍처를 도입했습니다. 이를 통해 트래픽 부하를 분산시키고 타임아웃 없이 안정적으로 전 매장에 작업을 하달할 수 있게 되었습니다.
  • [DB 쿼리 최적화] 상품 정보 조회를 위한 IN 절 ➔ EXISTS 절 튜닝
    • 문제 인지 (어쩌다 찾았는지): 중앙 관제 서버에서 특정 조건을 만족하는 상품 정보를 조회하는 API의 응답 시간이 데이터베이스 내 상품 데이터가 누적됨에 따라 눈에 띄게 느려지는 현상을 발견했습니다.
    • 원인 분석: EXPLAIN ANALYZE를 통해 쿼리 실행 계획(Execution Plan)을 프로파일링해 본 결과, 기존 IN 절을 사용한 서브쿼리가 수십만 건의 결과를 반환하면서 비효율적인 Full Scan과 반복 탐색이 발생하여 병목을 유발하는 것을 정확히 확인했습니다.
    • 해결 방법: IN 절을 EXISTS 절로 변경하여 쿼리를 튜닝했습니다. 이를 통해 DB 엔진이 조건을 만족하는 첫 번째 레코드를 찾는 즉시 스캔을 멈추게(Short-circuit evaluation) 유도하여 실행 계획 비용(Cost)을 크게 낮추고, 기존 15초 이상 소요되던 응답 시간을 0.2초 이내로 단축하여 30만건 상품 데이터 환경에서도 완벽한 조회 성능을 확보했습니다.
  • [DB 인프라] pgPool2 도입을 통한 커넥션 풀링 및 DB 부하 분산
    • 문제 인지 (어쩌다 찾았는지): 전국 400여 개 매장에서 동시다발적으로 DB 연결 요청이 집중되면서, PostgreSQL 서버의 커넥션 수가 한계치에 근접하여 응답 지연 및 연결 거부 오류가 간헐적으로 발생하는 것을 발견했습니다.
    • 원인 분석: 각 매장 서버 프로세스가 PostgreSQL에 직접 연결하는 구조여서, 동시 접속 수가 DB의 max_connections 한계를 초과하면 신규 연결 자체가 거부되는 병목이 발생했습니다.
    • 해결 방법: DB와 애플리케이션 사이에 pgPool2를 미들웨어로 도입했습니다. pgPool2의 커넥션 풀링(Connection Pooling) 기능을 통해 다수의 클라이언트 연결을 소수의 실제 DB 연결로 묶어 처리하도록 구성하여 DB 서버의 부하를 안정적으로 분산시키고 커넥션 고갈 문제를 해결했습니다.

    • 원인 분석: JPA 기반으로 작성된 Entity에서 유저 정보와 연관된 하위 테이블(부서, 권한 등)을 조회할 때, 1번의 메인 쿼리 이후 연관 데이터 개수(N)만큼 추가 쿼리가 무더기로 발생하는 N+1 문제가 원인이었습니다.
    • 해결 방법: 즉시 로딩이 필요한 데이터에 대해 Fetch Join(또는 @EntityGraph)을 적용하여, 연관된 유저 데이터를 단 한 번의 쿼리로 한꺼번에 가져오도록 최적화했습니다. 이를 통해 수백 번 발생하던 불필요한 단일 쿼리 호출을 제거하고 페이지 로딩 속도를 대폭 개선했습니다.

    • 원인 분석: S3에 적재된 파일을 Apache NiFi를 통해 PostgreSQL로 옮기는 과정에서 원본 데이터가 '일별' 단위로 적재되고 있었습니다. 사용자가 월별 데이터를 요청할 때마다 이 방대한 일별 데이터를 실시간으로 Grouping 연산하느라 DB I/O와 CPU 부하가 크게 발생한 것이 원인이었습니다.
